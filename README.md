# Запись на места (signup_seats)

Учебный проект по курсу «Безопасность высоконагруженных систем»: веб-приложение для записи на мероприятие с выбором места. Построено в микросервисной архитектуре.

## Компоненты

| Компонент  | Роль                                                              | Технология    |
|------------|-------------------------------------------------------------------|---------------|
| `gateway`  | Фронт: отдаёт страницу и проксирует `/api/` в `booking`            | nginx         |
| `booking`  | Бэк: REST API, работает с БД, кэшем и брокером                     | Go            |
| `notifier` | Отдельное действие: читает события из брокера, «отправляет» подтверждения (пишет в лог) | Go |
| `postgres` | База данных, основной узел (primary): места и записи               | PostgreSQL 16 |
| `postgres-standby` | База данных, резервный узел (standby): живая копия основного | PostgreSQL 16 |
| `redis`    | Кэш карты мест                                                     | Redis 7       |
| `rabbit1`, `rabbit2`, `rabbit3` | Брокер сообщений, кластер из трёх узлов: события `signup.created` / `signup.cancelled` | RabbitMQ 3.13 |
| `fw-*`     | Девять вспомогательных контейнеров, по одному на каждый компонент: держат сеть компонента и правила firewall | Alpine + iptables |

Всего 18 контейнеров: 9 компонентов и 9 `fw-*`.

## Запуск

Нужен Docker с плагином compose.

```
cp .env.example .env        # затем поменять пароли и секреты в .env
docker compose up -d --build
docker compose ps
```

Запуск занимает около минуты: команда ждёт, пока база, кэш и три узла брокера станут готовы, и только потом запускает `booking`, `notifier` и `gateway`. До этого страница http://localhost:8080 не открывается.

Проверка:

- страница с картой мест: http://localhost:8080 (выбрать место, записаться, отменить запись)
- API: `curl.exe http://localhost:8080/api/hello`
- RabbitMQ: http://localhost:15672 (узел rabbit1) и http://localhost:15673 (узел rabbit2), логин и пароль из `.env`
- состояние базы и брокера: `.\scripts\ha-status.ps1`

Остановка: `docker compose down` (с удалением данных БД: `docker compose down -v`).

После перезагрузки компьютера или если какой-то контейнер не поднялся, выполните `docker compose up -d`: команда запускает контейнеры в правильном порядке. Не используйте `docker compose restart` без имени сервиса: сервисы стартуют раньше своих `fw-*` контейнеров и падают. Перезапуск одного сервиса безопасен: `docker compose restart booking`.

Схема БД лежит в [db/schema.sql](db/schema.sql). PostgreSQL выполняет её один раз, при создании пустого тома. Если схема изменилась, пересоздайте том: `docker compose down -v`, затем `docker compose up -d --build`.

## API

| Метод и путь                | Что делает                         | SQL                                         | Ответы |
|-----------------------------|------------------------------------|---------------------------------------------|--------|
| `GET /api/hello`            | Заглушка hello-world (этап 2)      | —                                           | 200 |
| `GET /api/seats`            | Карта мест                         | `SELECT` (или чтение из кэша)               | 200, заголовок `X-Cache: HIT` / `MISS` |
| `POST /api/signups`         | Записаться на место                | `UPDATE seats` + `INSERT INTO signups`      | 201, 400, 404, 409 |
| `DELETE /api/signups/{id}`  | Отменить запись, освободить место  | `DELETE FROM signups` + `UPDATE seats`      | 204, 400, 401, 403, 404 |

Тело `POST /api/signups`: `{"seat_id": 1, "name": "Ivan", "email": "ivan@example.com"}`.
В ответе приходит `cancel_token` — секрет для отмены. Он показывается один раз, в БД хранится только его SHA-256. При отмене его передают в заголовке `X-Cancel-Token`.

Правило «одно место — один человек» держится на двух вещах:

1. `UPDATE seats SET status = 'taken' WHERE id = $1 AND status = 'free'` внутри транзакции: второй запрос на то же место не меняет ни одной строки и получает 409.
2. `UNIQUE (seat_id)` в таблице `signups`: БД сама не даст создать вторую запись на место.

## Сценарии этапа 3 (PowerShell)

Запись на место 1 (INSERT + UPDATE, публикация события):

```powershell
$body = '{"seat_id": 1, "name": "Ivan", "email": "ivan@example.com"}'
$s = Invoke-RestMethod -Method Post -Uri http://localhost:8080/api/signups -ContentType 'application/json' -Body $body
$s
```

Повторная запись на то же место — ошибка 409:

```powershell
Invoke-RestMethod -Method Post -Uri http://localhost:8080/api/signups -ContentType 'application/json' -Body $body
```

Кэш: первый запрос после изменения — `X-Cache: MISS` (чтение из БД и запись в кэш), второй — `HIT` (чтение из кэша):

```powershell
curl.exe -s -D - -o NUL http://localhost:8080/api/seats
curl.exe -s -D - -o NUL http://localhost:8080/api/seats
docker compose exec redis redis-cli GET seats:all
docker compose exec redis redis-cli TTL seats:all
```

Данные в БД (SELECT):

```powershell
docker compose exec postgres psql -U signup -d signup -c "SELECT * FROM seats WHERE status = 'taken'"
docker compose exec postgres psql -U signup -d signup -c "SELECT id, seat_id, name, email, created_at FROM signups"
```

Брокер: `booking` опубликовал событие, `notifier` его получил:

```powershell
docker compose logs booking notifier
docker compose exec rabbit1 rabbitmqctl list_queues name type messages consumers
```

Отмена записи (DELETE + UPDATE, публикация события):

```powershell
Invoke-RestMethod -Method Delete -Uri "http://localhost:8080/api/signups/$($s.id)" -Headers @{ 'X-Cancel-Token' = $s.cancel_token }
```

В командах `psql` подставьте свои `POSTGRES_USER` и `POSTGRES_DB` из `.env`, если меняли их.

## Этап 4: сегменты сети и firewall

### Сегменты

| Сеть       | Подсеть         | Кто в ней и с каким адресом |
|------------|-----------------|-----------------------------|
| `public`   | 172.28.1.0/24   | gateway `.10` |
| `internal` | 172.28.2.0/24   | gateway `.10`, booking `.20`, notifier `.30` |
| `data`     | 172.28.3.0/24   | booking `.20`, notifier `.30`, postgres `.40`, postgres-standby `.41`, redis `.50`, rabbit1 `.61`, rabbit2 `.62`, rabbit3 `.63` |

Наружу опубликованы только три порта: `8080` (gateway, для пользователей) и `127.0.0.1:15672`, `127.0.0.1:15673` (веб-консоли RabbitMQ, только с этого компьютера). Сеть `internal` помечена `internal: true`: из неё нет выхода за пределы Docker.

Сами сети уже разделяют компоненты: gateway не подключён к сети `data` и не видит базу. Но notifier и PostgreSQL находятся в одной сети `data`, и их разделяет только firewall.

### Как устроен firewall

У каждого компонента есть свой контейнер `fw-<имя>`:

1. `fw-<имя>` стартует первым, получает сетевые интерфейсы и адреса компонента.
2. Он применяет правила `iptables` из файла [firewall/rules/](firewall/rules/)`<имя>.rules` (скрипт [firewall/fw-apply](firewall/fw-apply)).
3. Сам компонент подключается к сети этого контейнера (`network_mode: "service:fw-<имя>"`).

Права менять правила (`NET_ADMIN`) есть только у `fw-*`. Сам сервис их не имеет: даже взломанный сервис не может отключить свой firewall. Правила переживают перезапуск сервиса, потому что сеть принадлежит `fw-*`.

Политика в каждом контейнере: всё запрещено (`DROP` для входящих, исходящих и транзитных пакетов), разрешены только loopback, пакеты уже установленных соединений и новые TCP-соединения из списка:

| Контейнер | Кто может подключиться | Куда может подключаться сам |
|-----------|------------------------|-----------------------------|
| gateway   | кто угодно на порт 80 | booking:8080 |
| booking   | gateway на порт 8080 | postgres:5432, postgres-standby:5432, redis:6379, rabbit1–3:5672 |
| notifier  | никто | rabbit1–3:5672 |
| postgres  | booking и postgres-standby на порт 5432 | никуда |
| postgres-standby | booking на порт 5432 | postgres:5432 (репликация) |
| redis     | booking на порт 6379 | никуда |
| rabbit1–3 | booking и notifier на порт 5672; другие узлы кластера на порты 4369, 25672 и 35672–35682; этот компьютер на порт 15672 (только rabbit1 и rabbit2) | к другим узлам кластера на порты 4369, 25672 и 35672–35682 |

Порты кластера RabbitMQ: 4369 — поиск узлов, 25672 — обмен данными между узлами, 35672–35682 — ответы для утилиты `rabbitmqctl`.

Все правила в системе:

```powershell
.\scripts\fw-show.ps1
```

Разрешённые соединения проходят, запрещённые нет (27 проверок, запрещённые ждут по 2 секунды):

Одна проверка вручную: booking достаёт до базы, notifier в той же сети — нет:


## Этап 5: надёжность

### Что добавлено

- **База данных: primary и standby.** `postgres-standby` при первом запуске копирует основной узел (`pg_basebackup`), затем непрерывно получает от него все изменения (потоковая репликация, асинхронная). Он доступен только для чтения. `booking` знает оба адреса и использует тот узел, который принимает запись (`PGHOST=postgres,postgres-standby`, `PGTARGETSESSIONATTRS=read-write`).
- **Брокер: кластер из трёх узлов.** Очередь `notifier.signups` имеет тип quorum: её копия есть на каждом узле, и она работает, пока живы два узла из трёх. `booking` и `notifier` знают все три адреса и при потере узла подключаются к следующему.
- **Резервные копии:** скрипты `db-backup.ps1` (`pg_dump`) и `db-restore.ps1` (`pg_restore`), файлы лежат в папке `backups`.

Состояние базы и брокера в любой момент:

```powershell
.\scripts\ha-status.ps1
```

### Сценарий 1: отказ узла брокера (переключение автоматическое)

```powershell
.\scripts\ha-status.ps1                       # три узла, лидер очереди
docker compose kill -s SIGKILL rabbit1        # некорректное завершение узла
# записаться на место на странице http://localhost:8080
docker compose logs --tail 8 booking notifier # "connected to broker node rabbit2", "confirmation sent"
.\scripts\ha-status.ps1                       # работают два узла из трёх, лидер сменился
docker compose start rabbit1                  # вернуть узел, он сам входит в кластер
```

Пока `rabbit1` не работает, кластер виден в консоли второго узла: http://localhost:15673.

### Сценарий 2: резервное копирование и восстановление

```powershell
# записаться на несколько мест на странице
.\scripts\db-backup.ps1         # файл появляется в папке backups
# отменить записи на странице (или сделать новые): данные изменились
.\scripts\db-restore.ps1        # вернуть состояние на момент копии
```

После восстановления страница показывает места так, как они были в момент копии. Записи, сделанные после копии, пропадают.

### Сценарий 3: отказ основной базы (переключение одной командой)

Этот сценарий показывайте последним: обратное переключение не автоматизировано.

```powershell
.\scripts\ha-status.ps1                        # postgres = PRIMARY, postgres-standby = STANDBY
docker compose kill -s SIGKILL postgres        # некорректное завершение основного узла
# попытка записаться на странице: ошибка
docker compose logs --tail 6 booking           # "connection refused" и "read only connection"
.\scripts\pg-promote-standby.ps1               # standby становится основным узлом
# запись на странице снова работает, прежние записи на месте
.\scripts\ha-status.ps1                        # postgres-standby = PRIMARY
```

Что делает `pg-promote-standby.ps1`:

1. Запрещает старому основному узлу принимать запись (кладёт в его данные файл `standby.signal`). Если его контейнер потом запустится, он будет доступен только для чтения. Так исключается ситуация с двумя основными узлами с разными данными.
2. Выполняет `pg_ctl promote` на резервном узле.

Номера новых записей после переключения идут с пропуском (например, 35 после 2): PostgreSQL резервирует номера пачками, это нормально.

Вернуть систему в исходное состояние (с сохранением данных):

```powershell
.\scripts\db-backup.ps1
docker compose down -v
docker compose up -d --build
.\scripts\db-restore.ps1
```

### Параметры обслуживания

Измерено на этом стенде:

| Что | Время |
|-----|-------|
| Отказ узла брокера: от `kill` до доставки следующего события через другой узел | около 6 с, автоматически |
| Отказ основной базы: работа скрипта переключения | около 3 с |
| Резервная копия (`pg_dump`) | около 1 с |
| Восстановление (`pg_restore`) | около 1 с |
| Запуск всей системы с нуля | около 1 мин |

Выбранные значения:

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| SLO доступности записи на место | 99,5 % в месяц | Это 3,6 часа допустимого простоя за 720 часов. Запись на мероприятие не критична по секундам: человек может повторить попытку через несколько минут. Более строгие 99,9 % (43 минуты в месяц) потребовали бы автоматического переключения базы и круглосуточного дежурства, которых в проекте нет. |
| SLI | доля запросов к `/api/`, завершившихся без ошибки 5xx | Считается по журналу `gateway`. Автоматического подсчёта в проекте нет. |
| MTTR, отказ узла брокера | 10 с | Переключение автоматическое, измерено около 6 с. |
| MTTR, отказ основной базы | 5 мин | Само переключение занимает 3 с, остальное — время, чтобы человек заметил отказ и выполнил одну команду. |
| MTBF | 720 ч (один отказ в месяц, требующий действий человека) | Это допущение, а не измерение: за время проекта отказов не наблюдалось. Взято с запасом в худшую сторону. |
| RPO при отказе базы | до 1 с записей | Репликация асинхронная: транзакция, подтверждённая за мгновение до отказа, может не успеть дойти до резервного узла. |
| RPO при восстановлении из копии | равно интервалу между копиями: 1 ч во время регистрации, 24 ч в остальное время | Данных мало, копия занимает 1 с, поэтому частые копии ничего не стоят. |
| RTO при полном восстановлении | 15 мин | Запуск с нуля 1 мин, восстановление 1 с, остальное — проверка. |

Проверка, что значения согласованы: доступность = MTBF / (MTBF + MTTR). При MTBF = 720 ч и MTTR = 5 мин получается 720 / 720,083 = 99,99 %, что лучше SLO. Весь месячный бюджет ошибок (3,6 ч) расходуется только в одном случае: отказ базы ночью, когда его никто не замечает несколько часов. Именно поэтому SLO выбран 99,5 %, а не строже.

### Ограничения

- Все контейнеры работают на одном компьютере. Реплики защищают от отказа процесса или контейнера, но не от отказа самого компьютера.
- Переключение базы выполняется вручную. Старый основной узел не возвращается в пару автоматически: исходное состояние восстанавливается пересозданием системы.
- `gateway`, `booking`, `notifier` и `redis` работают в одном экземпляре. При отказе Redis приложение продолжает работать, читая карту мест из базы.
- Кластеру брокера нужны два живых узла из трёх.
